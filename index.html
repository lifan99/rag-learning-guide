第 01 章 · 基础与入库

从一个问题理解RAG系统

能沿一次员工提问说明资料如何入库、证据如何被找到、答案如何引用原文，并画出各模块的输入输出。

我们要做一个企业内部知识库。员工问：“我入职六个月，能申请培训补贴吗？”虚构制度 training/v2 规定：“员工在职满一年，且培训在报名之前获得主管批准，才能申请培训补贴。每个自然年度补贴上限为 2,000 元。”先把这一次问答讲清楚，整套系统的职责就会逐渐显现。

把回答看成使用证据完成的任务

模型能写出通顺的中文，却不会自动知道公司今天执行哪份制度。要回答这个问题，系统先要拿到有效制度，再检查员工描述是否满足其中的条件。RAG 即检索增强生成，把寻找外部资料与组织答案连接起来：资料提供依据，生成模型负责结合问题解释依据。

这里的核心对象是问题、证据和答案。问题包含用户关心的事实，例如入职时长；证据包含制度条件，例如满一年、报名之前获得主管批准；答案应把两者对应起来。若只找到了补贴金额而遗漏申请资格，模型得到的材料就不足以可靠完成判断，因此必须检查进入生成阶段的具体内容。

证据还需要来源。回答中的“制度规定”应该能指向文档版本、章节和片段，让员工进一步确认适用范围。模型生成的引用编号由本次证据集合限定，再由程序映射回真实来源。这样，一句结论就能沿引用回到原文，而不是停留在看起来可信的表达。

用入库和查询两条路径组织工作

入库路径发生在资料新增或更新时：读取原文件，解析正文与结构，切成可检索片段，为片段生成向量，最后写入检索索引。切分后的记录继续保存文档身份和来源位置。一次准备完成后，多次提问可以复用索引，不必重复处理整套资料。

查询路径从员工问题开始：接收问题及用户身份，确定可查询的资料范围，检索相关片段，再选择适合放入模型的证据。生成模型读取问题与证据，输出答案和引用。检索像寻找相关页码，生成像根据这些页码整理说明，两步的输入输出都可以单独观察。

这两条路径通过文档版本连接。制度更新时，新内容经过入库流程形成新的可查询版本；查询选择当前有效资料。原文、解析文本、片段和回答因此构成一条可追溯链。排查错误时沿链逐步回看，能发现条件是在解析、切分、检索还是回答阶段丢失。

让技术栈服从清楚的职责

Flask 负责接收网页请求并返回响应；Python 服务函数组织业务步骤；LangChain 可以连接加载器、切分器和模型接口；Milvus 保存向量并检索候选；嵌入服务生成表示，Qwen 根据证据生成回答。先理解每个组件接收什么、输出什么，调用顺序才会有意义。

存储也按职责区分：原文件保存可重新处理的资料；业务记录保存文档身份、版本和访问范围；检索索引保存面向快速查找的片段与向量。早期这些职责可以由本地文件、简单数据库和一个向量库承担。模块清楚之后，再根据实际数据量调整部署方式。

练习使用 CRUD-RAG 的公开中文新闻，学习同样的数据处理与检索流程；培训补贴制度用于贯穿企业规则的推演。新闻语料和问题答案分别管理，评测程序保留参考答案，问答系统通过检索获得证据。这样既能练工程，又能检查一次回答到底使用了哪些资料。

第 02 章 · 基础与入库

Python对象与数据建模

能为文档、片段与检索结果定义数据对象，说明共享引用的影响，并在数据入口执行明确校验。

制度最初可能只是一个字符串，但进入系统后还要知道它的编号、版本和来源。若不同函数随意约定字典键名，文档经过几次转换就容易丢字段。本章从这些数据的含义出发，把 Python 对象变成稳定的模块接口。

从一段文字到有名字的数据对象

先区分文档与片段。文档表示一份具有身份和版本的资料，片段表示它的一部分正文及来源位置。两者都包含文字，却承担不同责任。给这些概念命名后，函数签名就能表达转换关系，例如解析得到文档，切分接收文档并返回片段列表。

dataclass 适合定义以字段为主的数据对象。它可以根据注解生成初始化、显示和相等比较等常用方法，省去重复代码。字段需要反映业务含义：document_id 表示身份，version 表示版本，text 表示内容。不要只追求字段齐全，应让每个字段都有明确的产生者和使用者。

对象之间优先通过组合表达关系。片段包含来源信息，检索结果包含片段和分数，回答包含文字与引用。检索结果不是文档的一种特殊制度，因此无需为了复用几个字段建立很深的继承树。组合让不同职责独立变化，也让阅读者更容易顺着字段追踪数据。

python
from dataclasses import dataclass, field

@dataclass
class Document:
    document_id: str
    version: str
    text: str
    tags: list[str] = field(default_factory=list)

@dataclass(frozen=True)
class Chunk:
    document_id: str
    version: str
    start: int
    end: int
    text: str

doc = Document("training", "v2", "Eligibility: one year of service.")
chunk = Chunk(doc.document_id, doc.version, 0, len(doc.text), doc.text)
assert (chunk.document_id, chunk.version) == ("training", "v2")
assert doc.text[chunk.start:chunk.end] == chunk.text
doc.tags.append("policy")
assert Document("another", "v1", "Other text").tags == []
print(chunk)

沿引用理解修改怎样传播

Python 变量名绑定到对象。把文档对象赋给另一个名字，不会产生第二份文档；两个名字仍指向同一对象。函数接收对象后，如果原地修改其中的标签列表，其他持有该列表的代码也会观察到变化。因此必须先决定函数是否有权修改输入，而不是遇到问题再补拷贝。

浅拷贝只新建外层容器，内部列表和字典仍可能共享。深拷贝递归复制对象图，适合需要独立嵌套数据的场景，但复制范围越大，成本和语义越难把握。对于检索结果，常常只需新建一个带分数的包装对象，就能避免为排序而改动原始文档。

可变默认值也属于共享问题。dataclass 中用 default_factory=list，让每次创建文档时得到独立标签列表。frozen=True 可以限制字段重新赋值，适合表达创建后保持稳定的记录；若字段内部仍放可变列表，它并不会递归冻结列表，因此字段类型也要配合数据所有权设计。

在入口校验，在内部表达契约

类型注解帮助阅读者和静态工具理解接口，但不会自动执行输入校验。外部 JSON 传来的编号可能是数字，正文可能为空，位置也可能颠倒。应在数据进入内部模型前检查类型与约束，让下游代码接收到已经满足约定的对象，而不是每一层重复猜测字段是否存在。

Pydantic 等工具可以把字段解析和运行时校验组织起来，也可能根据配置进行类型转换。是否接受数字转换成字符串，要由接口契约决定；需要保持严格类型时就明确设置。字段通过校验后，仍需检查业务关系，例如片段结束位置不能超过正文长度，引用的文档版本必须确实存在。

模型越清楚，修改越局部。将来把 Milvus 替换成其他检索实现，适配器只要继续返回同一种检索结果，生成服务就能继续工作。先稳定数据含义，再引入框架对象，可以让业务代码保持可读，也让测试能够用少量普通对象构造完整场景。

迭代器、文件与数据入口

能逐条读取和校验 JSONL，定位损坏记录，为规范化文档生成稳定标识，并明确资源关闭与重复导入行为。

第一份制度可以复制进程序，几千篇新闻则需要可靠的数据入口。导入任务既要知道读到了哪里，也要知道某条记录为什么失败，还要在重跑时认出已经处理过的文档。文件读取因此是入库流程的第一层工程设计。

先确定记录边界，再开始流式读取

JSONL 把每条 JSON 记录放在单独一行，适合逐条处理。项目内部可以统一采用这种格式，但上游资料未必如此：CRUD-RAG 问答文件包含问题、答案和关联新闻字段，新闻语料还要按实际格式确认文档边界。换行是排版还是记录分隔，直接决定一篇文章会不会被拆错。

可迭代对象提供迭代器，迭代器逐次返回元素并保存当前位置。生成器使用 yield 暂停函数，下次取值时从原位置继续，因此读取、校验和转换可以逐条衔接。已经耗尽的生成器需要重新创建才能再次读取，不能把它当成可以任意回放的列表。

流式处理的收益来自只保留当前记录及有限批次。若最后把所有结果转成列表，或者无限积压待处理任务，内存仍会随数据量增长。应同时控制读取、批处理和写出之间的缓冲，并保留文件名与行号，让任何一条坏记录都可以被重新找到。

下面使用自拟的检查记录演示入口契约：body 必须是字符串，空白行跳过，错误带来源名和行号；流由调用方用 with 管理。示例只把两条记录转成列表以检查结果，大文件应逐条消费。

import json
from io import StringIO

def scan_json_lines(text_stream, source_name):
    for row_no, raw_line in enumerate(text_stream, start=1):
        if raw_line.strip() == "":
            continue
        location = f"{source_name}:{row_no}"
        try:
            record = json.loads(raw_line)
        except json.JSONDecodeError as cause:
            raise ValueError("Malformed JSON at " + location) from cause
        if type(record) is not dict:
            raise ValueError("Expected an object at " + location)
        body = record.get("body")
        if not isinstance(body, str):
            raise ValueError("Expected a string body at " + location)
        yield {"source": source_name, "line": row_no, "body": body}

example = '{"body": "Pump check"}\n\n{"body": "Valve check"}\n'
with StringIO(example) as memo:
    rows = list(scan_json_lines(memo, "checks.jsonl"))
assert [row["line"] for row in rows] == [1, 3]
assert memo.closed
print([row["body"] for row in rows])

把失败和资源生命周期纳入接口

入口要定义空行、缺字段和解析失败的处理方式。调试阶段可以遇到坏记录立即停止；批处理也可以记录失败并继续，但必须输出成功数、失败数和失败位置。两种策略都需要明确，避免跳过记录后仍把整个文件报告为完整导入。

with 将文件生命周期包在清楚的范围里，代码块正常结束或抛异常时都会执行对应的退出逻辑。让调用方打开文件、生成器消费文件流，可以在提前结束时清楚控制关闭时机。清理文件句柄与撤销已写入的数据是不同职责，批任务仍需记录已经完成的工作。

异常应携带能够定位的问题上下文，例如来源文件、行号和失败阶段。转换成领域异常时保留原始原因，就能同时看到输入位置与底层解析错误。正文中不混入报错文字，日志也不把整份敏感资料作为错误消息；后续重试依据记录状态重新处理相应项目。

让同一份资料在重跑时仍有同一身份

文档身份、内容版本和处理结果应分开。文档编号表示这份资料是谁，内容摘要帮助判断文字是否变化，片段编号还取决于文档版本、切分配置和位置。修改制度后仍可能是同一份文档的新版本；两份部门制度文字相同，也可能拥有不同的授权与管理关系。

稳定标识需要确定的序列化方法和明确摘要算法。对约定字段排序后编码成字节，再计算 SHA-256，同样输入在重跑时会得到同样结果。Python 内置 hash 不适合跨进程持久身份；如果预处理会替换空白或符号，还应记录规范化规则，明确摘要针对哪一种内容。

使用稳定标识后，重复导入可以按键覆盖或跳过已完成结果，从而避免重复堆积。完整重建还要保存来源、解析配置和切分配置。问题与参考答案作为评测材料单独管理，入库正文来自指定语料；这样数据身份同时服务于重试、来源追踪和后续实验比较。

python
import hashlib
import json

def stable_id(namespace, fields):
    payload = json.dumps([namespace, fields], ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()

left = stable_id("document-version", {"document_id": "training", "text": "Policy text"})
right = stable_id("document-version", {"text": "Policy text", "document_id": "training"})
assert left == right
print(left)

按职责组织模块，让导入保持可预测

Python 导入模块时会执行顶层代码，并缓存模块对象。因此函数和类型定义可以放在模块中，而下载数据、创建索引和启动服务应放在明确入口。使用 python -m 包名.模块名运行入口，让包关系清楚，避免靠随意修改搜索路径解决导入问题。

import unittest

class FakeRetriever:
    def __init__(self, rows):
        self.rows = rows

    def search(self, question):
        return list(self.rows)

def find_sources(question, retriever):
    return [row["document_id"] for row in retriever.search(question)]

class QueryTests(unittest.TestCase):
    def test_returns_sources(self):
        retriever = FakeRetriever([{"document_id": "training"}])
        self.assertEqual(find_sources("Eligibility?", retriever), ["training"])

    def test_empty_result(self):
        self.assertEqual(find_sources("Unknown?", FakeRetriever([])), [])

if __name__ == "__main__":
    unittest.main()

解析先恢复文档原有的结构

解析负责把文件转换成文字和结构，切分负责把解析结果组织成检索单位。处理文本时先确认标题、段落和记录边界；处理 PDF 时还要确认阅读顺序、页码与表格位置。文字提取顺序错误时，后续切分再精细，也只是把错乱内容分成更小的块。

结构给文字提供解释。标题说明段落谈什么，表头说明数字属于什么字段，脚注可能修改适用条件。把“2,000”从“年度培训补贴上限，单位元”中单独取出来，就丢掉了含义。解析输出应尽量保留章节关系、表头和单位，再决定怎样转成适合检索的文本。

清理步骤同样需要保留信息。页眉页脚可以按规则处理，正文中的换行和空白则要结合格式理解。扫描件通过 OCR 得到文字后，仍需检查数字和阅读顺序。原文件与规范化文本都保留，才能在发现解析问题时重新处理，并解释片段位置采用哪一份文本作为基准。

在语义完整与长度预算之间选择边界

片段越长，越容易保留完整条件，也越可能混入多个主题；片段越短，匹配更聚焦，却更依赖相邻内容。先按标题和段落寻找自然边界，再把过长部分继续拆分，能让多数片段保持可独立理解的主题。制度的资格、额度和流程常可作为起点，但例外必须跟相关规则一起考虑。

长度预算应使用实际模型对应的分词器。token 是模型输入单位，汉字数、字符串长度和 token 数并不相同；嵌入模型与生成模型还可能使用不同分词器。标题前缀和来源说明也会消耗预算，因此记录片段正文长度之外，还应检查真正送入模型的完整输入。

重叠让相邻片段共享部分内容，能够减轻边界处的条件丢失，但也增加向量化成本、存储和重复命中。选择重叠时应看哪些语句跨越边界，并比较固定问题的结果。若一个规则需要多段共同解释，可以保留父章节关系，在检索命中后扩展相邻证据。

每个片段应带文档编号、版本、章节和位置。对规范化文本可使用左闭右开的字符范围 start:end，取该范围就得到正文。给片段补充标题时，标题可以作为检索前缀单独保存，原正文的范围仍保持明确，从而支持直接检查引用是否准确。

纯文本字符位置不能直接充当 PDF 页码，清理前后的偏移也可能不同。解析阶段应建立适合来源的定位信息，例如页码与段落编号，或规范化文本偏移及对应原文位置。片段身份还应包含切分配置版本，配置改变后就能区分新旧索引并重新建立引用。

def paragraph_chunks(text):
    start = 0
    for paragraph in text.split("\n\n"):
        end = start + len(paragraph)
        if paragraph.strip():
            yield {"text": paragraph, "start": start, "end": end}
        start = end + 2

text = "Eligibility: one year of service.\n\nManager approval is required before enrollment."
chunks = list(paragraph_chunks(text))
for chunk in chunks:
    assert text[chunk["start"]:chunk["end"]] == chunk["text"]
assert len(chunks) == 2
print([(chunk["start"], chunk["end"]) for chunk in chunks])

向量表示与相似度

能解释文本怎样进入向量空间，手算余弦与点积，并区分表示质量、精确近邻搜索和近似索引的影响。

员工说“培训能报销吗”，制度写“培训费用补贴”，两者未必共享完全相同的词。我们希望检索能识别这类表达联系。嵌入模型把文字转换成可比较的向量，再由相似度与索引帮助寻找候选证据。

下一步：召回与排序

从 token 序列到文本表示

分词器先把文本转换成模型接受的 token 序列，再映射为整数编号。编号只是词表中的位置，编号相近不表示含义相近。嵌入模型经过学习，把整段输入映射为固定维度的数值向量，使某些相关表达在所用相似度下更接近。

一个向量的每个坐标通常不对应人能直接命名的单一属性。可以把整体理解为模型为文本分配的位置，但不能把某一维随意解释成补贴金额。检索效果取决于模型的训练目标、语言和领域适配，因此需要用实际问题验证哪些相关表达能够被拉近。

问题和文档必须按照兼容的模型规范编码。有些模型要求查询与文档使用不同输入角色或前缀，这些规则成套定义了比较方式。相同维度只表示数组长度一致，不表示属于同一空间；更换模型或表示规则时，应让文档向量与查询编码一起更新。

用长度和方向理解相似度

点积把对应坐标相乘后求和：q·d = Σqᵢdᵢ。它同时受到向量长度与方向影响。余弦相似度再除以两者的长度，cos(q,d) = (q·d)/(‖q‖‖d‖)，从而比较方向；非零向量的余弦值位于负一到一之间，值越大表示方向越接近。

把每个非零向量除以自身长度，就得到单位向量。两个单位向量的点积等于原向量的余弦相似度，因此归一化后可以用点积实现同样排序。零向量没有可用的余弦方向，应在输入校验时处理。是否归一化则应遵循模型与检索度量的配套设计。

欧氏距离衡量两个向量之间的几何距离，值越小越近；点积和余弦通常按值越大越相似排序。单位向量还有 ‖q-d‖² = 2-2(q·d) 的关系。数学排序约定要与数据库配置一致，检索分数表示某种空间关系，答案是否正确仍取决于证据内容。

python
from math import sqrt, isclose

def dot(left, right):
    if len(left) != len(right):
        raise ValueError("dimension mismatch")
    return sum(x * y for x, y in zip(left, right))

def cosine(left, right):
    denominator = sqrt(dot(left, left) * dot(right, right))
    if denominator == 0:
        raise ValueError("zero vector")
    return dot(left, right) / denominator

query = (1.0, 0.0)
a = (1.0, 0.0)
b = (2.0, 2.0)
assert dot(query, b) > dot(query, a)
assert cosine(query, a) > cosine(query, b)
assert isclose(cosine(query, b), 1 / sqrt(2))
print(cosine(query, a), cosine(query, b))

从逐个比较走向近似近邻索引

有 N 个 d 维向量时，逐个计算相似度需要约 O(Nd) 的评分工作，再选择最高的若干项。这种精确搜索容易理解，也适合作为小规模基线。数据增长后，逐次扫描全部向量会消耗更多时间，因此向量库建立附加索引来减少查询时访问的候选。

近似近邻搜索利用图结构、分区等方式寻找很可能接近的向量。它用一定的索引构建成本和额外空间换取查询速度，也可能遗漏精确搜索会找到的邻居。搜索范围、候选数量和数据分布都会影响结果，应同时记录延迟与相对精确搜索的邻居覆盖情况。

这里存在两层检查：首先看近似索引是否找回向量空间中的近邻，再看这些近邻是否真的包含回答所需证据。如果精确搜索本身选错材料，增加索引搜索范围不会改善表示；若精确搜索很好而近似结果漏项，就应研究索引参数。分清这两层，才能定位优化方向。

手算点积为什么会改变排序

输入查询向量 q=(1,0)，候选 A=(1,0)，候选 B=(2,2)。点积为 q·A=1、q·B=2，因此按原始点积排序时 B 在前；B 较大的长度参与了这个结果。

计算余弦：A 的长度是 1，B 的长度是 √8，所以 cos(q,A)=1，cos(q,B)=2/√8≈0.707。按方向比较时 A 在前。将 B 除以 √8 后，它与 q 的点积也变为约 0.707。

输出是两套明确的排序及其原因。把这个过程迁移到真实检索时，先确认模型推荐的度量与归一化约定，再用固定问题检查候选证据，而不是单凭分数数值判断回答质量。

下一步：上下文与答案

让正确证据进入候选集合

召回的目标是以可接受的代价，找到一批可能支持回答的片段。向量检索把问题编码到与文档兼容的表示空间，适合连接“培训费能报多少”与“年度学习补贴额度”这样的不同表述。近邻索引帮助减少搜索工作；近邻本身反映表示空间中的相似性，是否支持业务结论还需要查看原文。

BM25 从词项匹配出发，结合词频、词的稀有程度和文档长度排序。制度编号、员工类别和专有名词可能为它提供强信号。中文分词和编号处理决定哪些词能够匹配，因此分析器也属于实验配置。向量与关键词各自返回一组候选，可以利用两种信号的互补性。

查询服务先取得可信身份对应的授权范围和有效版本，再把同一范围传给两路检索。每条结果携带文档、版本、片段 ID 和原始得分，便于后续核对。召回数量控制搜索宽度：取少了可能漏掉资格条件，取多了则增加去重、重排和生成成本，需要通过题集寻找适合的范围。

用排名融合不同检索信号

两路结果合并时，先识别同一版本的同一片段，避免它占据多个名额。措辞相似但适用对象不同的制度应继续保留；仅按文本相似度去重可能删掉重要区别。原始余弦分数与 BM25 分数通常尺度不同，直接相加会让数值范围较大的一路主导排序。

RRF 使用名次融合。某片段在一路的排名为 r，这一路贡献 1/(c+r)，不同路贡献相加，缺席的一路贡献零。平滑常数 c 调节靠前名次的优势，与最终返回数量 K 是两个参数。这样可以先建立不依赖分数校准的基线，再根据实验决定是否需要加权或其他融合方法。

下面的函数接收各路按相关性排列的片段 ID，输出融合后的 ID。每一路内部先去重，排名从一开始，分数相同用 ID 决定稳定顺序。它只处理排序，来源和权限元数据仍由外部映射保存。稳定输入和确定性输出使我们能够逐步复算结果，而不是只观察一个最终答案。

python
from collections import defaultdict

def reciprocal_rank_fusion(rankings, c=10):
    scores = defaultdict(float)
    for ranking in rankings:
        unique_ids = dict.fromkeys(ranking)
        for rank, chunk_id in enumerate(unique_ids, start=1):
            scores[chunk_id] += 1 / (c + rank)
    return sorted(scores, key=lambda item: (-scores[item], item))

print(reciprocal_rank_fusion([["A", "C", "B"], ["B", "A", "D"]]))

重排器对问题与已有候选做更细的相关性比较，常见实现会联合处理二者。它有机会把已经召回但位置较低的材料向前移动；若审批条件根本没进入候选，重排无法补出这条信息。因此要分开记录召回池与重排后结果，先判断证据是否存在，再判断位置是否合理。

下一步：分步评测

从 token 到逐步生成

Tokenizer 把文本转换成 token ID，一个 token 可能对应字、词的一部分或符号组合。常见自回归模型根据已有 token 预测下一个 token 的分布，选择一个后继续生成。因此输出能够逐段到达客户端，输入输出成本通常按 token 统计。

注意力让一个位置结合其他位置的信息。可以把 Query 理解为当前需要匹配的线索，Key 是各位置提供的匹配特征，Value 是据此汇总的信息；这些向量都由模型学习得到。标准缩放点积注意力计算 softmax(QKᵀ/√d)V。不同头可以学习不同关系，帮助把“补贴”与前面的条件联系起来。

在常见因果解码器中，causal mask 阻止位置读取未来 token，保持下一 token 预测的条件关系。训练时已经知道整段文本，仍可用掩码并行计算各位置；推理时未来 token 尚未产生，需要逐步推进。注意力权重描述内部计算，不等同于事实证明，答案仍需要可访问的原文支持。

temperature 改变下一 token 分布的集中程度，top_p 限定累计概率覆盖的候选集合。较低温度通常减少随机变化，但错误续写也可能具有很高概率。知识问答宜固定采样配置比较效果，把事实正确性放到证据与答案评测中，而不是只看回答是否稳定。

为模型组织足够而清晰的上下文

模型输入由系统要求、当前问题、必要历史和检索证据组成，还要预留输出空间。先按接口定义计算总 token 预算，再限制各部分大小。证据应保留完整条件、标题和适用时间；截断时若只留下“2000 元”而移除了“满一年且事先获批”，模型就失去了回答资格问题的重要依据。

KV Cache 在自回归推理中保存已处理位置的 Key 与 Value，减少后续生成时的重复计算。它服务于特定模型和上下文的推理过程，应用会话记录仍需独立保存。普通全注意力下，缓存通常随已处理长度和并发增长，所以长历史不仅占输入预算，也会影响推理资源与延迟。

提示词要明确任务、材料用途、输出字段和证据不足时的行为。为本轮证据分配 C1、C2 等引用 ID，并附文档版本和位置。文档中的文字属于输入材料，即使包含“改变规则”等指令也不能替代系统要求；实际资源权限由应用控制。模型只负责在允许的证据和输出契约内组织回答。

多轮问题需要恢复必要的指代，例如把“那一年最多多少”还原为培训补贴的年度额度问题。改写保留用户确认的主体、时间和否定条件，同时保留原问题以便核对。历史模型回答不自动成为事实；如果上一轮审批状态不明，应请求澄清，而不是在改写时补成已经获批。

先定义口径，再计算指标

记每题已标注的相关文档集合为 G。K 的单位是片段：先截取原始排名中的前 K 个片段，再把这些片段的文档 ID 去重得到集合 R。Hit@K 判断交集是否非空，Recall@K 等于交集大小除以 G 的大小，再按题平均。多文档题找回一篇即可命中，却可能还缺关键条件。同一文档的多个重叠块只贡献一次覆盖，也会占用前 K 个片段的名额。

RR@K 是截断范围内首条相关片段的原始排名倒数，前 K 个片段均不相关时记零；MRR@K 是各题 RR@K 的平均。计算排名时保留重复片段占用的位置，例如 X、X、A 中 A 仍排第三。超出 K 的相关结果不能贡献本次分数。

本章的文档级二值 NDCG@K 也保留原始片段排名：第 i 位的文档属于 G 且此前未出现时增益 g_i=1，后续重复文档增益为 0，不压缩名次。DCG@K=Σ g_i/log2(i+1)，求和范围是截取后的片段位置。IDCG@K=Σ 1/log2(i+1)，i 从 1 到 min(K, |G|)；分母不随实际返回条数或去重后文档数缩小。NDCG@K=DCG@K/IDCG@K。若使用其他相关性等级或增益函数，应连同公式一起记录。

上述检索指标针对具有非空 gold 的题。无答案题单独衡量正确拒答，同时统计可回答题被错误拒答的比例。生成质量分别观察关键事实正确、条件完整、与给定证据一致及引用支持；忠实复述过期材料仍可能不符合实际业务，所以来源版本也是评分条件。

平均指标之外，要保存每题候选、最终上下文、答案、引用和评分理由。自动裁判可以帮助扩大评测量，但需用人工样本校准，并记录裁判配置。耗时分位数、失败率和成本与质量一起报告，才能判断新增重排的收益是否足以覆盖额外等待与调用。

from math import log2

def rank_metrics(gold, returned, k):
    gold = set(gold)
    if not gold or type(k) is not int or k < 1:
        raise ValueError("nonempty gold and positive integer k required")
    seen = set()
    rr = dcg = 0.0
    for rank, document_id in enumerate(returned[:k], 1):
        if document_id in gold and document_id not in seen:
            if rr == 0.0:
                rr = 1 / rank
            dcg += 1 / log2(rank + 1)
        seen.add(document_id)
    idcg = sum(1 / log2(rank + 1)
               for rank in range(1, min(k, len(gold)) + 1))
    return {"rr_at_k": rr, "ndcg_at_k": dcg / idcg}

if __name__ == "__main__":
    print(rank_metrics({"A", "B"}, ["A", "A", "A"], 3))
    print(rank_metrics({"A"}, ["X", "Y", "A"], 2))

先把一次 HTTP 请求读成普通程序交互

客户端是发出请求的程序，例如浏览器或 curl；服务端是等待请求并处理它的程序。访问 http://127.0.0.1:8000/ask 时，127.0.0.1 是本地回环地址，8000 是服务监听的端口，/ask 是应用路由。IP 找到主机或网络环境，端口区分接收连接的程序，路由再选择处理函数。

localhost 通常解析到本地回环地址；域名由 DNS 查询成可连接的地址。本例常见的 HTTP/1.1 通过 TCP 连接传递消息；HTTPS 在其上保护传输并验证服务器身份。其他 HTTP 版本可能采用不同传输，当前先沿这条本地链路理解。Windows、WSL 与容器有各自网络配置，不要把 localhost 当成任意环境都共用的服务器地址。

请求由方法、路径、请求头和正文组成。GET 常用于读取 /health，POST /ask 提交一次问答；Content-Type: application/json 说明正文格式，JSON 承载 question 等数据。响应也有状态码、响应头和正文。下方是字段结构示意，实际 HTTP 客户端会处理消息长度等细节。

第 10 章用 /v1/answers 与 request_id 演示接口设计；配套第 19 章程序实际使用 /ask 与 trace_id。学习契约时可以比较两者，运行实验时以 service_lab/README.txt 为准，不能直接把示例路径当作已实现接口。

连接被拒绝时，先确认进程是否启动、监听在哪个地址和端口；收到 404 或 400 则说明已到达某个 HTTP 服务，要检查路由或输入。连接超时与响应读取超时处于不同等待阶段；客户端超时只说明没有及时得到结果，不能证明服务端未执行动作。写操作因此需要第 12、21 章的幂等与结果查询。读懂下一节状态码后，应能解释一条成功响应和一条失败响应。

先约定一次请求的输入与结果

把问答定义为 POST /v1/answers，请求正文提供 question 和可选会话标识，身份来自可信认证过程。响应包含 request_id、status、answer、citations，引用保留文档版本和位置。status 可区分 answered、needs_clarification 与 insufficient_evidence；它表达问答结果，与 HTTP 层是否成功处理请求共同构成契约。

HTTP 400 表示输入不符合契约，401 表示缺少有效身份，403 表示资源无权访问，429 表示请求超出限额，503 可以表达依赖暂时不可用。服务正常查询后发现证据不足，可以返回 HTTP 200 加业务状态。这样前端能决定是让用户补充问题、重新登录，还是稍后重试。

校验从正文类型、字段类型、长度和允许值开始，再进入业务授权与会话归属判断。类型注解帮助读代码，但不会自动验证网络输入；Pydantic 等工具也只执行所定义的规则。即使 JSON 结构正确，客户端声明的部门仍需要权限系统核验。请求体上限、问题长度和返回字段一起限制接口资源消耗。

让路由保持简单，让依赖可以替换

Flask 路由负责 HTTP 解析、基本校验和响应转换；QueryService 负责授权范围、检索、上下文和回答流程；模型与索引通过适配器调用。创建应用时注入 service 和认证函数，测试即可替换成可控的 fake。下面只展示这层连接，服务返回约定结果，统一异常处理器再把超时等异常映射成稳定错误结构。 在第四章创建的虚拟环境中运行 python -m pip install Flask 准备依赖，保存应用工厂后，可通过 Flask 的 test_client 对接口发起本地测试请求。

资源也要有明确所有者。可安全复用的客户端或连接池通常随服务进程创建和关闭；数据库事务、请求标识和当前用户随一次请求结束。Flask 的 g 属于上下文存储，通常与请求同寿命，不能作为跨请求聊天记录库。会话和任务需要持久化，避免进程重启或多副本后丢失。

部署时，Flask 应用由生产 WSGI 服务承接请求，入口代理再处理 TLS、请求大小和连接超时。增加进程或线程会影响每个进程的客户端、连接池和内存占用，应按负载测量。业务模块先保持清晰接口，同一代码库即可运行，无需先把每个模块拆成独立网络服务。

from uuid import uuid4
from flask import Flask, jsonify, request

def create_app(service, authenticate):
    app = Flask(__name__)
    app.config["MAX_CONTENT_LENGTH"] = 16 * 1024

    @app.post("/v1/answers")
    def answer():
        request_id = str(uuid4())
        principal = authenticate(request)
        if principal is None:
            return jsonify(error="unauthorized", request_id=request_id), 401
        if not request.is_json:
            return jsonify(error="json_required", request_id=request_id), 415
        body = request.get_json(silent=True)
        question = body.get("question") if isinstance(body, dict) else None
        if not isinstance(question, str) or not 1 <= len(question.strip()) <= 2000:
            return jsonify(error="invalid_question", request_id=request_id), 400
        result = service.answer(question.strip(), principal)
        return jsonify({**result, "request_id": request_id})

    return app

用流式协议传递进度与最终答案

完整 JSON 适合先生成、核验再返回。若希望更早显示进度，可以使用 SSE：响应类型为 text/event-stream，以空行分隔事件，事件可以命名为 progress、delta、final 和 error。SSE 描述服务端向浏览器的单向事件流；浏览器原生 EventSource 通常用 GET，POST 问答可以通过 fetch 读取事件流，或先创建请求再订阅结果。

流开始前完成身份、输入和证据检查，并发送正确响应头。开始发送正文后，就不能再把 HTTP 200 改成 503；后续失败要通过事件说明，客户端根据 final 判断是否完成。若前端把断流前的一段文字当最终答案，用户可能看到缺失资格条件的结论，因此完成状态属于协议的一部分。独立 SSE 小实验只在固定 fake 输出通过字段、引用 ID 和固定证据文本匹配后发送 final；这仅验证这一小型确定性样例的契约，真实答案的事实、条件完整性和引用支持仍需另行评测。

Flask 可以用生成器逐段返回内容。进入生成器前尽量提取所需请求数据，确需访问上下文时使用相应支持；生成器结束或客户端断开时释放上游流和连接。代理缓冲、空闲超时与心跳也会影响实际展示。分别测首段到达时间和完整耗时，才能看出流式带来了什么体验变化。

把已懂的职责迁移到 FastAPI

当前可运行项目选用 Flask，检索与模型调用仍是普通 Python 对象。FastAPI 使用相同的 HTTP 概念，常用 Pydantic 模型表达输入、依赖声明提供合作对象，并生成 OpenAPI 接口描述。OpenAPI 描述如何调用接口，不代替权限检查或业务正确性测试。先迁移边界，再考虑换整个项目。

若目标岗位使用 FastAPI，先只迁移一个 /ask 路由：保持 Engine.ask、请求字段和结果含义不变，用 Pydantic 严格约束 question 与 top_k，声明依赖错误的状态码，再复用有效请求、空输入、未知字段、布尔 top_k 和依赖失败等用例。FastAPI 默认校验错误常为 422，当前 Flask 示例为 400；决定是否对齐并记录，不能默认为完全相同的契约。

当前 Engine.ask 内含阻塞客户端，适合先使用 FastAPI 的普通 def 路由，由框架在受控线程池运行；直接写成 async def 不会把阻塞调用变成异步。真正异步时，需要整条等待链使用可等待接口，并处理超时与取消。WSGI 和 ASGI 是 Python 应用与服务器之间的接口约定，前者用于当前 Flask 部署，后者支持异步应用交互；服务器名称不代表模型推理自动加速。

此处提供迁移目标与验收依据，没有提供已验收的 FastAPI 服务。先完成现有 Flask 链路；目标岗位明确需要时再做这一个薄适配，并把实际版本、命令和测试记录纳入作品。

下面的 Pydantic 2 示例仅定义请求数据，不启动 FastAPI 服务。它拒绝额外字段和非严格类型，限制 question 原始长度与 top_k 范围，再检查并清理问题两端空白；HTTP 错误转换、身份与业务调用仍由路由负责。

from typing import Annotated
from pydantic import (
    BaseModel, ConfigDict, Field, StringConstraints, model_validator,
)

class QueryInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    question: Annotated[
        str, StringConstraints(strict=True, min_length=1, max_length=2000)
    ]
    top_k: Annotated[int, Field(ge=1, le=8, strict=True)] = 3

    @model_validator(mode="after")
    def trim_and_check(self):
        normalized = self.question.strip()
        if normalized == "":
            raise ValueError("question needs visible text")
        self.question = normalized
        return self

if __name__ == "__main__":
    sample = QueryInput.model_validate({
        "question": "  maintenance records  ", "top_k": 2,
    })
    print(sample.model_dump())

预期：正常为 progress → delta → delta → final；注入超时为 progress → delta → error，没有 final。开始传输后 HTTP 状态仍为 200，因此客户端必须检查事件结束语义。输入错误在开始流之前返回 400；取消消费时生成器关闭上游。

这里校验了什么：events 在流结束后调用可注入的 finalizer 组装候选结果，再调用 validator。默认校验检查字段、answered 状态、非空文本和有效且不重复的引用，并将答案与固定的 C1 假证据逐字比较。空流、错误文本、无效引用或校验异常都以 error 结束，不发送 final；在发送 final 或 error 前关闭上游。这个固定样例的精确匹配只用于证明事件分支可控，不证明真实回答的语义正确性或证据充分性。

异步并发、资源与超时

能追踪协程的调度与等待，选择合适的任务组合方式，并为查询设置并发、队列和时间边界。

问答请求的大量时间可能花在等待网络：向量服务、关键词检索和模型 API 都不会立即返回。并发可以重叠互不依赖的等待，但还要回答三个问题：由谁调度、同时允许多少工作、到期后怎样停止。理解这些机制后，性能优化才有可预测的行为。

先认识进程、线程、等待与计算

进程是正在运行的程序实例，通常拥有独立内存；线程是进程内执行指令的工作单元，同一进程的线程共享许多对象。协程是可暂停、稍后继续的程序任务；asyncio 的事件循环在一个线程中调度这些任务，操作系统仍负责调度进程和线程。

I/O 是与网络、磁盘等交换数据。等待模型服务返回时，本地 CPU 往往有空；解析大量文字或计算向量则可能主要消耗 CPU。阻塞调用让当前线程等结果，异步可等待调用在等待时把执行机会让给其他任务。仅给函数加 async 并不会改变里面阻塞 SDK 的行为。

并发是让多个任务在同一段时间内推进；并行是同一时刻实际执行多个计算。对两路独立网络查询，并发的收益来自重叠等待；若两路争用同一限额或一条必须依赖另一条结果，收益会改变。先能把调用标成“等待”“计算”或“依赖前一步”，再读下面的 Task 与预算。

本次先解释一个现象：为何把阻塞模型 SDK 直接放入 async def 可能拖住其他请求？答案要沿“同一循环线程被占住 → 其他协程不能及时获得运行机会”说明。任务组、并发限制和取消随后解决的是如何有边界地组织这些等待。

协程怎样运行，Task 怎样组织

调用 async def 函数会得到协程对象，执行它需要被 await 或交给事件循环调度。await 表示等待一个可等待对象完成；只有真正需要等待时才可能把控制权交还循环，已经完成的操作不一定挂起。事件循环在可运行任务之间切换，所以同一线程可以处理许多等待中的网络请求。

依次写 await dense() 和 await bm25()，第二个调用会在第一个结束后开始。Task 把协程纳入调度，让两个独立查询有机会交错推进。gather 会并发组织可等待对象，结果顺序对应输入顺序；默认遇到首个普通异常会向等待者传播，其他任务通常不会因此自动取消。

TaskGroup 在一个作用域内创建并等待子任务，某个子任务出现普通异常时，会取消其他未完成任务，等待清理后汇总异常。它适合两路结果共同构成一次操作的情况。若产品允许一路失败后继续使用另一路，需要在子任务内把预期失败转换成明确结果，再由上层决定降级。

把并发量、速率与积压分别限制

Semaphore 控制同时进入某段代码的数量，适合限制正在调用外部服务的请求。速率限制控制一段时间内允许启动多少次调用，用来对应供应商配额。两者不同：即使并发只有两个，调用特别快时每秒仍可能发出很多请求，需要根据依赖的规则分别设置。

背压让下游容量不足反映到上游：使用有界队列、等待配额或拒绝新请求，避免无限创建 Task 占用内存。等待队列也消耗用户时间，应包含在请求总预算内。队列长度、等待时长和拒绝率提供了系统是否接近容量的证据，比只看模型调用耗时更完整。

下面示例使用 Python 3.11 及以上的 TaskGroup 和 timeout。gate 由同一事件循环中的协调者创建和共享，两路检索使用相同 scope；总预算包含等待 gate 的时间。实际服务还需按进程数估算总并发，多进程各自的信号量不会自动形成跨进程总限额。

把完整代码保存为 concurrent_retrieval.py，运行 python concurrent_retrieval.py。main 通过 asyncio.run 进入事件循环，分别创建容量为 1、2 的共享 gate；每轮两个请求的四路 fake 调用共用它。asyncio.sleep 只模拟可让出的等待，finally 归还模拟资源。断言检查 peak 分别为 1、2，结束后 inflight 为 0；不对机器相关的耗时作断言。

python
import asyncio

async def retrieve_pair(question, scope, dense, bm25, gate):
    async def call(search):
        async with gate:
            return await search(question, scope)

    async with asyncio.timeout(2.0):
        async with asyncio.TaskGroup() as group:
            dense_task = group.create_task(call(dense))
            bm25_task = group.create_task(call(bm25))
    return dense_task.result(), bm25_task.result()

async def run_demo(limit):
    gate = asyncio.Semaphore(limit)
    inflight = peak = 0

    async def fake_search(question, scope):
        nonlocal inflight, peak
        inflight += 1
        peak = max(peak, inflight)
        try:
            await asyncio.sleep(0.01)
            return question, scope
        finally:
            inflight -= 1

    questions = ("q1", "q2")
    scope = "department-A"
    results = await asyncio.gather(*(
        retrieve_pair(q, scope, fake_search, fake_search, gate)
        for q in questions
    ))
    assert results == [((q, scope), (q, scope)) for q in questions]
    assert peak == limit
    assert inflight == 0
    print(f"gate={limit}, peak={peak}, inflight={inflight}")

async def main():
    for limit in (1, 2):
        await run_demo(limit)

if __name__ == "__main__":
    asyncio.run(main())

超时与取消沿着调用链传播

总截止时间限制一次用户请求可以占用多久，各阶段超时再分配这笔预算。若总预算是两秒，已经排队一秒半，后续查询只有剩余时间可用，不能每层重新获得两秒。仅针对可恢复的暂时故障重试，并把退避、重试调用和结果检查都计入同一预算。

asyncio 超时通过取消推进协作式清理，协程应在 finally 或上下文管理器中释放连接和配额，再让取消继续传播。取消本地等待不保证远端已经停止计算，运行中的线程任务也通常不会被强制中断。涉及写操作时，需要幂等键或状态查询来判断实际结果。

Flask 的 WSGI 请求仍占用一个 worker；异步视图可以在请求内部并发 I/O。请求结束后仍需执行的工作交给持久任务系统。需要大量长连接时，再按负载比较 ASGI 方案，保持业务服务接口不变。

按瓶颈选择线程、进程和异步

异步网络客户端在等待时允许事件循环处理其他任务。阻塞 SDK 可以放入受限线程池；直接在 async 函数中调用阻塞方法或长时间计算，会占住循环线程。PDF 解析、OCR 等 CPU 工作可交给独立进程或 worker，与在线查询隔离资源。

常规启用 GIL 的 CPython 中，纯 Python CPU 密集代码通常不能靠多线程实现多核并行；释放 GIL 的扩展和可选 free-threaded 构建有不同条件。进程可以利用多核，同时需要付出数据传递与额外内存成本。选择应围绕实际瓶颈和依赖支持情况，再用测量验证。

单线程异步也可能竞争共享状态：读取后 await，再写回时，其他任务可能已修改它。优先使用请求私有变量，必要时在短临界区加锁，数据库状态借助事务和约束。明确状态所有者，也为下一章的重复任务处理奠定基础。

文档任务、版本与发布

能设计可恢复的入库状态机，用幂等和发布协议保持有效版本一致，并推演中断、重试与删除。

一次文档入库可能包含文件读取、解析和数百次向量写入，耗时远超过普通问答。把它变成后台任务以后，系统还要记住做到了哪里，以及什么结果已经可以被查询。我们用培训制度增加审批材料说明的新版，学习如何在旧版本继续服务时完成更新。

从上传请求变成持久任务

上传接口先校验身份和文件，保存不可变原件及内容哈希，再登记文档版本与任务。返回 202 表示已受理，需要保证任务已经持久化且能够恢复调度。入库任务 ingest_status 使用 queued、processing、validated、published、failed；用户通过 job_id 查询具体阶段和可操作的失败原因。文档的访问状态 document_status 与删除后的清理任务 cleanup_status 分别保存，入库成功不代表文档始终允许访问。

小系统可以让 worker 扫描任务表。引入消息队列后，业务数据库写入成功但消息未发出，会造成任务失联；先发消息再提交数据库，也可能让 worker 读到不存在的任务。outbox 把任务记录和待发送事件放进同一个数据库事务，再由投递器读取已提交事件并发送。

投递器发出消息后可能来不及记录成功，恢复时会再次发送，因此 outbox 解决登记与投递的衔接，还需要消费者处理重复。任务表保存权威进度，队列帮助调度，缓存提高读取速度，三者职责清楚后，重启时才知道应恢复哪些工作，而不是只依赖进程内的一个 Task。

worker 领取任务时应通过条件更新或租约避免无协调的重复执行，并记录尝试次数与最近错误。租约到期可重新领取；旧 worker 迟到的结果需要用版本或领取标记检查，防止覆盖新执行的状态。阶段产物保留明确身份，才能把恢复动作限制在尚未完成的部分。

用稳定标识衔接重试与版本发布

幂等指同一逻辑操作重复执行后，业务结果保持一致。把知识库、文档版本、处理配置和片段位置纳入稳定 chunk_id，向量写入采用按 ID 覆盖或已完成检查。任务在“向量已写入、状态未更新”时崩溃，再执行不会生成另一批随机 ID 的副本。外部调用费用仍可能重复，需要阶段缓存或供应商支持进一步减少。

新版本先进入独立的暂存 generation，解析、切块、Embedding 与索引元数据全部在此完成。验证内容哈希、块数、模型维度和来源位置，再按在线读取所用的一致性策略确认可查询。写入接口返回成功与查询客户端能够读到这批数据，是两个需要衔接的时点。

验证通过后，在业务数据库发布有效版本或 generation 指针。查询依据指针过滤，并在材料外发与输出前复核；一份回答对同一文档使用确定版本。SQL 事务能够原子更新业务记录，却不会自动包住外部向量库，所以先准备可读产物、后发布指针，再清理旧产物构成整个发布协议。

小知识库可以维护各文档有效版本映射，大批量发布可以使用整库 generation 清单。两种方式都要明确回滚目标和缓存失效策略。嵌入模型或切块配置变化时，新索引与对应配置一起发布，避免问题使用新编码器而文档仍留在旧表示空间。

分别记录入库、访问与清理状态

暂时网络错误可在预算内退避重试；损坏文档和配置错误需修复后再运行。发布前失败时保留旧有效版本，暂存产物可继续处理或回收。发布后发现质量问题，可回到保留且可读的旧版本并恢复配置；回滚不能重新开放已撤销的访问权限。

文档访问状态 document_status 使用 active、revoked；active 仍需结合有效版本和调用者权限判断可访问性。删除先在权威业务层把 active 改为 revoked，使新请求不能访问该文档，再登记独立清理任务。cleanup_status 使用 pending、running、completed、failed，依次异步处理向量、缓存和按保留策略处理原件；失败后可以重新排入 pending。引用下载和缓存命中同样读取当前文档状态，不能绕开撤销。

这三个状态属于不同对象：入库任务可以保持 published，文档已经 revoked，清理任务同时处于 failed。清理失败只触发清理重试，不能把文档恢复为 active，也不把已完成的入库任务改成失败。这样才能同时回答“版本是否曾发布”“目前能否访问”和“残留数据是否清完”。

为每次任务保存输入版本、处理配置、阶段耗时和错误类别，便于恢复时核对事实。用故障演练检验协议：中途停止 worker、重复投递、延迟索引可见性、发布后删除。预期结果应写成可以观察的状态和查询行为，随后才能判断实现是否真正满足设计。

先用一张表理解持久状态与事务

表把同类记录放在一起，列表示字段，行表示一条记录；主键唯一识别一行。SQL 的 INSERT、SELECT、UPDATE 分别用于写入、读取和修改。下面只用 Python 自带 SQLite，先理解数据为何能跨进程保留，再阅读后面的文档版本模型。

Python 字典属于当前进程内存；SQLite 文件保存在磁盘，关闭连接后用同一路径重新打开仍能读取已提交记录。连接 :memory: 得到的是临时内存库。Redis 常把数据放在内存中并可配置持久化，但本项目把它用作可重建缓存；申请结果与权限事实另有权威存储。存储工具的能力与项目赋予它的职责要分开。

事务把相关数据库改动组成一次提交；失败可回滚，防止只完成一半。唯一约束限制重复身份，参数化 SQL 把值作为参数传入，不用字符串拼接用户输入。事务不能自动覆盖另一个 Milvus 或外部报销服务，后面再处理跨系统发布。

预期打印 ('pending',)：修改因异常回滚，重新打开文件仍读到先前提交的状态。独立改成成功提交后应读到 running，再加入同主键重复写入并解释约束错误。脚本结束时临时目录会清理；正式项目改用明确持久路径。四表模型、PostgreSQL 执行计划与复杂发布是后续展开，不是这次基础实验的前置条件。

import sqlite3
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as folder:
    path = Path(folder) / "lesson.sqlite3"
    db = sqlite3.connect(path)
    db.execute("CREATE TABLE jobs (id TEXT PRIMARY KEY, state TEXT)")
    with db:
        db.execute("INSERT INTO jobs VALUES (?, ?)", ("j1", "pending"))
    try:
        with db:
            db.execute("UPDATE jobs SET state=? WHERE id=?", ("running", "j1"))
            raise RuntimeError("injected failure")
    except RuntimeError:
        pass
    db.close()
    db = sqlite3.connect(path)
    try:
        row = db.execute("SELECT state FROM jobs WHERE id=?", ("j1",)).fetchone()
        assert row == ("pending",)
        print(row)
    finally:
        db.close()

先掌握 Redis 基础与旁路缓存

首次接触服务和存储时，先完成第 10 章“HTTP 基础”和第 13 章“持久状态与事务”小节。Redis 是另一个可通过客户端访问的服务；本章内存替身只模拟缓存接口，真实连接仍要指定地址、端口和超时。

Redis 按键保存带类型的值。先认识五种常用类型：String 保存文本、数字或序列化 JSON；Hash 按字段读写对象；List 保存有顺序的元素；Set 保存不重复成员；Sorted Set 为成员附加排序分数。本实验用 String 保存一份完整答案，暂不涉及集群运维。

旁路缓存（cache-aside）先 GET，命中则复用结果；未命中才回源计算，再 SET 并附带 TTL。业务更新先提交权威数据，再使相关缓存失效。TTL 是剩余有效时间：SET key value EX 30 将写入和 30 秒有效期放在同一命令，TTL key 返回剩余秒数；-1 表示未设过期，-2 表示键不存在。

过期由 TTL 控制；淘汰是内存达到配置限制时按策略移除条目，例如 LRU 或 LFU。未到期的键也可能被淘汰，某些策略会拒绝新增写入，因此应用必须能处理未命中和缓存写入失败。缓存不是权威事实的唯一副本。

先从减少同一问题的重复计算入手。用回源调用次数证明是否复用，再在真实 Redis 接入后测命中率、错误率和端到端耗时。内存字典可以演练状态变化，但不能据此宣称 Redis 的网络延迟、并发容量或真实模型效果。

把三类缓存故障与负载变化对应起来

穿透是反复查询不存在的数据，每次都回源；先校验输入，对确实不存在且允许缓存的结果可使用短 TTL 的空值标记。空结果也受身份和版本范围约束，错误或无权访问不能随意缓存成“没有资料”。

击穿是一个热门键失效，许多请求同时回源；可在应用内合并同一键的并发计算，并为回源设置限额。雪崩是大量键集中失效或缓存整体不可用，引发成批回源；可分散 TTL、限流并明确降级行为。分布式锁和集群故障切换在出现对应并发与可用性需求后再研究。

把登录身份变成服务端可信的访问范围

认证确定调用者身份，授权决定该身份可以访问哪些对象。服务端收到令牌后，按约定校验签名、算法、有效期、签发者与受众，再取得当前租户和角色。请求中的租户编号可以是选择条件，但不能自行赋予权限；最终范围必须与经过认证的身份相交。

把授权结果整理成统一访问上下文，包含用户、租户、可访问知识库和权限版本。普通员工能查询制度并读取自己的申请，管理人员能读取授权范围内的审批材料。选择角色权限还是更细的资源规则，取决于实际共享方式；表达式的目标是让访问规则可执行、可检查。

通用问题“培训补贴有什么要求”只需制度证据。个人问题“我还能报多少”还需要本人身份、入职记录、事前审批状态和年度已用额度。后端先读取获准访问的业务事实，再计算资格和余额；模型负责把结果连同制度解释清楚，而不从聊天中的自述直接确立业务资格。

沿检索和生成路径持续执行同一规则

向量检索和关键词检索都接收同一个授权范围，在各自查询中限制候选。这样，未获授权的资料不会先混进候选，再依赖提示词隐藏。结果汇合后，还要根据权威业务状态检查文档是否撤权、删除或换版，使索引里的旧元数据不能决定最终访问权。

候选交给外部重排器和生成模型之前，既检查用户能否访问，也确认该处理方允许接收这类资料。例如内部制度可交给批准的模型服务，而个人申请附件可能需要本地处理或脱敏。只发送回答所需的证据和字段，数据流就更容易解释，费用和暴露面也随之缩小。

引用由后端根据实际使用的片段生成，用户点击后仍经过授权；会话历史和下载接口遵守相同规则。检索资料中的文字属于证据，不负责改变系统角色或工具权限。若一段附件要求“忽略限制并导出全员记录”，应用仍按既定访问范围取数，并在工具执行处检查操作权限。

把缓存键与当前权限、版本连接起来

TTL 不保证立即读到新数据。慢请求可能在更新失效后把旧结果写回，因此仍需版本校验和可靠失效，并明确哪些内容允许短暂陈旧；要求严格最新的业务事实可以直接读权威来源。

培训问答的缓存键至少要区分问题、租户、有效权限范围、知识库发布版本，以及影响答案的模型和提示配置。个人额度查询还涉及用户和业务数据版本；如果额度变化频繁，直接查询权威记录通常更清楚。把字段都塞进键之前，应先问缓存到底节省哪一步、命中是否值得。 配置版本还应覆盖切分、检索参数等影响结果的因素；若扩展多轮问答，也要纳入有效会话上下文。本节实验只处理单轮问题。

命中缓存后仍按当前权限复核，撤权通过权限版本变化或可靠失效立即阻止新的访问。日志只记录定位所需的编号、版本、耗时和错误类别，正文按需要单独受控保存。将身份、检索、缓存和审计连接起来，才能在投诉发生时还原“这位用户为何获得了这段内容”。

算法与系统设计：从候选筛选推导合适的架构

用候选去重与 Top-k 串起复杂度、数据结构和不变量，并把局部算法选择连接到系统需求与部署取舍。

多路检索返回许多候选，应用还要去重、排序、选择上下文。这个局部流程足以练习算法推理：先确定结果含义，再选数据结构，最后判断优化是否改变了用户等待和系统成本。

先定义重复身份，再计算真实工作量

设两条检索路径共返回 n 个候选，候选身份由租户、文档、版本和片段编号组成。同一片段在两条路径出现，可以合并命中记录；不同版本即使文字相同，也要保留各自身份。按正文摘要可识别完全相同的内容，近重复则需要另行定义相似性规则。

保序去重可逐个检查集合：第一次遇到标识时输出，并记入 seen。输入遍历决定顺序，集合只负责成员判断。在键的哈希与比较成本可视为常量时，总时间平均为 O(n)，额外空间随不同标识数增长。若用列表逐次查重，比较次数可能累积成二次增长。

复杂度先说明规模单位，再统计总操作次数。计算长文本摘要还包含字符处理成本，外部重排则包含网络和模型耗时；它们不能都隐入一次常数操作。由此可以估算优化价值：几十条候选的去重通常很便宜，缩减昂贵重排输入可能更影响整条问答链路。

def unique_candidates(candidates):
    seen = set()
    for item in candidates:
        key = tuple(item[name] for name in
                    ("tenant_id", "document_id", "version", "chunk_id"))

围绕一个不变量推导 Top-k

候选已经得到可比较的统一分数后，目标是保留最高的 k 条。k 接近总数时直接排序通常清楚；当输入很长而 k 很小时，维护大小不超过 k 的最小堆，让堆顶代表当前入选集合中最弱的一项，新分数只有超过它才值得替换。 示例先用最多 k 个输入建堆，再用 heappushpop 保留每一步较大的 k 个值；重复分数按出现次数保留。

循环不变量是：处理前 i 个输入后，堆保存其中最高的至多 k 个分数。初始为空成立；未满时直接加入，已满时淘汰最小项或忽略更弱项，都维持这个性质。有限实数输入下，k≥1 时遍历上界为 O(n log(k+1))，额外空间 O(k)，最后有序输出还需排序。

真实候选还要规定并列时的顺序，例如按原始位置稳定处理，并在比较键中加入可排序序号。向量相似度与关键词原始分数往往量纲不同，应先用已经定义的融合或重排策略得到排序依据。堆负责维护排名，评分规则负责说明“更好”的业务含义。

python
from heapq import heapify, heappushpop
from itertools import islice


def largest_k(scores, limit):
    # Input contract: scores are finite real numbers; duplicates are retained.
    if type(limit) is not int or limit < 0:
        raise ValueError("limit must be an integer >= 0")
    stream = iter(scores)
    selected = list(islice(stream, limit))
    if not selected:
        return []
    heapify(selected)
    for score in stream:
        heappushpop(selected, score)
    selected.sort(reverse=True)
    return selected


assert largest_k([-1.0, 0.4, 0.4, 0.9, 0.2], 3) == [0.9, 0.4, 0.4]
assert largest_k(iter([0.2, 0.8]), 5) == [0.8, 0.2]
assert largest_k([0.8], 0) == []

把同样的推理方法迁移到数据与架构

二分查找适用于已经排序并具有单调条件的数据。例如制度按生效日期排序，可寻找不晚于查询日的最近起始日期，再核对结束日期和授权。半开区间的更新必须保留明确不变量；搜索位置约需对数次比较，但在列表中插入新制度仍可能移动大量元素。

入库依赖则是图问题：解析完成后才能切分，片段准备好才可向量化，核验成功后才能发布。拓扑排序给出满足前置依赖的顺序，并能发现环；实际执行还要考虑失败传播、并发资源与幂等。把依赖顺序和运行状态分开，工作流才能既讲得清楚又恢复得起来。

系统设计同样从约束推导选择。先估计峰值请求、资料变化和权限范围，再测主要耗时与资源争用。小团队可使用模块化应用加 Worker；只有独立扩容、发布节奏或团队边界产生实际需求时，再拆分服务。每次增加组件，都应说明改善哪项指标，以及多出的通信、状态和维护成本。

LoRA 保留基础权重 W，训练低秩更新 BA，使 W′=W+sBA。若权重大小为 d_out×d_in、秩为 r，新增矩阵参数量约为 r(d_in+d_out)，因此可减少可训练参数与相关训练开销，具体资源仍取决于模型和配置。

上下文工程：让每一次模型调用拿到恰当的信息

为问题、历史、证据和工具描述分配预算，保留关键事实，并把模型结果验证为可执行的数据。

同样的模型和检索器，给出不同的上下文，可能得到不同答案。一次培训问答需要完整制度；一次申请办理还需要本人事实、审批状态和当前额度。本章沿这些信息的来源和用途，学习如何选择、组织、更新与检查模型实际看到的输入。

先确定每类信息承担什么责任

系统要求说明任务与输出契约，用户消息表达本次需求，检索证据提供制度依据，业务工具返回当前事实，历史帮助解释指代。先标明每类内容的角色，才能决定哪些必须保留、哪些可以压缩。把全部文本按时间拼接容易让旧答案、当前事实和引用混在一起。

例如“那这门课还能报多少”需要从历史恢复课程与申请金额，却应重新读取本年度已用额度。用户曾经说“还没批准”也可能后来获得批准，因此权限与业务状态由当前权威数据确定。检索问题的改写用于补全明确指代，同时保存原问题；无法确认的条件继续保持未知。

上下文工程把这些选择做成可观察的步骤：记录选了哪些材料、采用哪个版本、删去了什么，以及为何删去。提示模板仍是其中一部分，但材料选择、历史整理和工具结果的形状同样影响回答。这样排查问题时，能够直接比较两次模型输入，而不是只比较最后答案。

用预算选择完整信息，再考虑压缩

设一次请求允许的上下文容量为 C，输出预留为 O，系统与工具描述为 S，当前问题为 Q，历史为 H，证据为 E，安全余量为 M，则需要满足 S+Q+H+E+O+M≤C；同时检查提供方是否另设输入和输出上限。数值由所选模型和实际 tokenizer 决定，不能用一个固定的“中文字符换算率”替代所有模型。

第 19 章的字符预算适合先演示选择机制。配套 context_lab 进一步统计序列化消息的 UTF-8 字节，默认单位为 utf8_bytes_proxy，用于重复观察选择过程；它并不等于模型 token 数。可选 --tokenizer 指向本地分词器后，以匹配的聊天模板计算输入 token，代码明确取得 token ID 列表再计数。云接口可能额外包装输入，仍应保存 usage 校核并留出余量。

预算不足时，先去除重复片段与无关历史，再以完整条款为单位选择证据。资格条件、例外、单位和有效期应该随金额一起进入上下文。需要压缩时，让摘要保留事实来源与未解决问题；把“审批未知”压成“审批完成”会改变业务含义，比多占几行文本更严重。

让结构化输出与事实核验各尽其责

读懂一次工具调用循环

应用把目标、必要状态和工具描述交给决策器，决策器返回工具名称与参数，执行器校验后运行工具，再把结果交回下一轮。模型生成的 tool call 本身没有读取数据库或创建申请；实际动作发生在应用执行器。由此可以分别检查“选择是否合适”和“执行是否符合规则”。

模型可调用 lookup_policy、lookup_employee 和 prepare_application，分别查询制度、读取本人事实和准备草稿；额度由程序计算，提交由宿主的 Store.approve 在确认后执行。身份从运行上下文取得，工具不接受模型随意指定另一个员工来扩大访问范围。输入检查涵盖名称、字段、类型和金额；输出提供可消费的结果或明确错误，使下一步可以据此继续、澄清或停止。

离线决策器按预定路径返回工具请求，帮助稳定复现中断与重复调用；模型决策器通过真实 API 选择工具，可能走出不同路径。两种运行共用执行器与持久状态。评价模型决策能力时使用真实模式，评价提交幂等和恢复行为时，可以用受控路径覆盖每个故障位置。

把 ReAct、工具调用和循环控制对应到代码

ReAct 将推理与行动交替组织：围绕目标选择动作，执行后取得外部观察，再根据观察继续。工具调用是模型表达动作及结构化参数的一种接口；loop 是应用推进下一轮并执行退出规则的控制程序。三者有关联，但仅仅发出一次 tool call 还没有构成可靠的 Agent。

在本实验中，driver.decide 产生 action，工具执行器校验后获得 observation，history 保存两者并供下一轮使用。调试记录应包括动作、参数、返回、业务状态与停止原因；无需要求模型输出私有的逐字思考过程。ScriptedDriver 用预定选择帮助观察控制流，LiveDriver 才能检验模型的实际决策表现。

状态不能只是一串对话。可信身份、run_id、当前业务状态、待确认草稿、已完成调用与预算都需要明确归属。上下文超限时只保留必要事实和可追溯结果，不能因摘要丢掉用户未确认或权限变化的信息；第 20 章提供预算与历史取舍实验。

运行器在模型和工具调用前检查剩余活动时间，并把剩余预算交给支持超时的接口；工具返回后再检查，超时结果不能继续进入等待确认。MCP 读取桥最多等待剩余预算或 5 秒中的较小值，超时请求取消本地 future。同步工具与 SQLite 等待无法被此检查强行抢占，取消也不保证远端停止，因此这是协作式预算，不是严格的墙钟终止保证。等待人工确认的离线时间不计入 active_seconds；上下文限额是 UTF-8 字节而非 token。真实接入还应在调用前预留费用或 token 上限，并记录实际 usage。

把确认、提交和恢复写成状态变化

MCP 实战：把知识与业务能力接入 Agent

沿一次请求区分三个角色

Host 是组织模型、会话与工具的应用；Client 是 Host 中负责某个 MCP 连接的组件；Server 提供可访问的工具、资源或提示模板。培训助手是 Host，制度查询进程是 Server，连接两者的 SDK 会话属于 Client。一个应用可以连接多个服务，各服务继续负责自己的数据与业务实现。

模型侧 tool calling 表达“想调用哪个工具及其参数”，MCP 负责客户端如何发现和请求服务端能力。应用可以把 MCP 工具描述转成模型支持的工具定义，再把选中的调用交给 Client。模型无需直接读写协议报文，MCP 也不会自动替应用决定下一步应该选择哪个工具。

协议与 SDK 会演进，实验安装使用配套依赖文件中的版本，连接生命周期由该 SDK 管理。理解时重点跟踪能力发现、参数结构、请求、结果和错误；不要把不同版本的握手或消息格式混在一个程序中。升级后重新运行同一客户端调用测试，可以及时发现契约变化。

先运行本地 stdio，再解释远程变化

在 stdio 模式下，客户端启动服务端子进程，通过标准输入与标准输出交换协议消息。服务端自己的调试文字应写入标准错误，避免把普通日志混进协议流。客户端退出时关闭会话并清理子进程，才能避免一次次演示留下悬挂进程。

配套 MCP 服务使用已验证的 mcp==2.3.0，暴露 lookup_policy 与 lookup_employee；客户端发现工具并读取结构化结果。服务端用具体输出模型声明字段，客户端先检查错误标志，再读取结果。加上 --agent 后，两次读取真正经过 MCP，草稿与确认提交继续留在上一章的宿主执行器中。

将来使用远程 Streamable HTTP 时，服务生命周期、网络超时、身份凭证和并发都需要重新配置。传输成功说明消息到达，应用仍要确认调用者能否读取目标资料。身份应来自经过验证的连接或业务上下文，而不是把模型生成的 employee_id 当作授权凭证。

让工具描述、结果与执行规则一致

一个好的工具描述应说明何时使用、需要哪些参数、返回哪些事实和哪些情况会失败。例如“查询本人培训资格”应返回资格相关事实与检查结果，避免把各种无关员工数据都塞回模型。工具越容易正确选择和使用，后续上下文就越简洁。

发现工具后，Host 可以只向模型开放本轮任务需要的子集；Server 仍对每次实际请求执行参数和权限检查。服务返回文本即使包含“再查询所有员工”等指令，也只作为不可信工具结果处理。模型的下一次建议还要经过同一执行规则。

测试分三层：协议层验证客户端确实发现并调用服务；业务层验证结果符合制度和身份；Agent 层验证模型在合适时机选择工具并利用结果。能直接调用工具不代表 Agent 一定会选对它，把三层分开才能定位工具描述、连接或决策的具体问题。

统一评测与观测：证明答案正确，也证明事情办成

为 RAG 与 Agent 建立分层判定，比较质量、任务完成、成本和延迟，并用失败样本安排下一次修改。

知识库回答“最多补贴多少”，主要检查证据与结论；Agent 回复“申请已提交”，还必须检查系统中是否真的存在正确申请。两种系统可以共用问题、配置和追踪记录，但成功条件需要分别定义。本章把第 9 章的检索评测扩展成完整应用的验收过程。

从用户目标定义成功，再选择评分方法

RAG 可以分层检查：候选是否覆盖相关资料，最终上下文是否保留条件，答案是否正确，引用是否支持结论。Agent 继续检查工具参数、关键执行顺序和最终业务状态。问答题的关键事实可以人工标注；申请题则可以直接查询数据库核对申请人、金额与数量。

有些过程约束必须满足，例如提交前确认；另一些路径可以有多种合理实现，例如先查制度还是先查本人资格。评分应固定真正的业务要求，避免强迫每次调用都复制某条参考轨迹。只要必要事实充分、访问合法且最终结果正确，不同有效路径都可以成功。

确定性检查适合字段、金额、引用集合和数据库结果；人工评分适合解释是否完整；模型裁判可帮助扩大语义评测量，但需要用人工样本校准。将裁判结论与理由保存，抽查误判，再决定哪些指标能够用于自动发布判断。

无答案题沿用第 9 章“用自己的小题集记录真实问答质量”的分流：service_lab 自动 evaluate 要求非空 gold_document_ids；应通过 /ask 单独运行无答案问题，再人工检查拒答与依据并记录结果。不要把空 gold 填进检索命中率分母，也不要把 HTTP 成功或确定性校验当成语义正确。

让一次比较具有可重复的实验条件

每次运行保存数据版本、题目清单、模型标识、提示配置、检索参数与代码版本。开发题用于分析失败，保留题用于验收选定方案。CRUD-RAG 适合练检索问答；培训申请场景补充权限、确认、重复提交和恢复题，使评测覆盖实际业务动作。

真实模型会带来随机变化，同一任务可以多次独立运行，记录每次成功与失败。聚合时报告样本数、重复次数和失败类别，避免把少数成功演示解释为稳定能力。受控决策器适合验证执行器的机制，真实模型模式用于观察工具选择和语言理解，结果分别汇总。

比较方案时先提出假设，例如“历史摘要遗漏审批未知状态，导致多提交申请”。只改变相关上下文规则，检查该类任务改善多少，以及普通问答、输入用量和延迟是否退化。保留逐题配对记录，比只比较两个总平均数更容易解释改动效果。

把招聘文字翻译成能展示的工作

先分清两条岗位主线。AI 应用方向需要可运行的 HTTP 服务、检索与回答质量、数据与缓存、配置测试和部署记录；Agent 方向在此基础上补工具循环、状态、终止、权限和失败恢复。掌握一种相关框架的实际迁移能力有价值，但技术名称不能代替你自己的实现与证据。

百度 2026 年 7 月 21 日发布的大模型研发校招岗 J100679 提到 Python、模型 API、RAG、Agent，以及调用链路的响应速度与稳定性。对这一类应用岗位，可以展示第 19 章的服务、一次可解释的评测和一次超时处理，再用现场代码说明你能修改其中的核心逻辑。

百度 2026 年 9 月 20 日发布的 Agent 后端岗 J106087 进一步涉及记忆、MCP、权限、状态持久化、重试、链路追踪与质量评估。它提示进阶工程工作如何从问答扩展到持续执行的系统；第 21—23 章提供对应练习，但岗位所要求的经验仍应按实际招聘说明判断。 该社会招聘明确要求三年以上后端经验，这里只用来观察能力方向；不能把其中 Kafka、Kubernetes 等整套要求都当作初级第一项目的前置门槛。投递条件以自己选定的具体岗位为准。

读取其他岗位时也采用同样方法：把“熟悉 RAG”展开为数据入口、候选选择、证据生成和评测；把“工程落地”展开为可启动服务、持久状态、部署与排障；把“Agent”展开为工具选择、上下文、执行和结果检查。不同公司用词不同，这些可展示的工作更容易比较。

用四份材料支撑一次完整面试

第一份是运行入口：README 说明环境、依赖、数据、配置与启动命令，面试官或同伴能按步骤得到一次结果。第二份是架构与数据流：从培训问题走到原文、候选、实际上下文、答案与引用，再延伸到申请工具与业务记录。图上的每个模块都应该能对应到代码职责。

第三份是实验报告：说明题集、计分方法、基线、改动、改善与退化，用逐题记录支持判断。第四份是故障案例：演示模型超时、版本失效或提交后中断，解释如何定位和恢复。四份材料共同展示实现、验证与维护，比单独罗列框架名称更能支撑技术追问。

AI 辅助开发也可以自然纳入展示。选择一段生成后由你修改的代码，解释输入输出、为什么修改、怎样验证，以及还有哪些条件需要继续测试。现场再完成一个局部变化，例如增加字段校验或调整候选去重，能够说明你对最终实现承担了理解与检查的责任。

自查简历表述：只跑 fake 时写“离线契约与故障测试”，真实 Redis 接入要有真实实例的命令与输出；真实模型实验要有配置、题集和逐题记录；框架项目要能现场解释节点、状态与结束条件。没有实测的延迟、成本或准确率不填数字。结合自己的基础展示优势：例如用指标推导和误差分析说明数学能力，用接口、状态和故障处理展示工程能力。

按问题选择下一项技术，而不是同时扩张所有方向

若目标业务大量使用扫描件、表格和图示，优先扩展文档布局与多模态证据：保存页码和区域，比较 OCR、表格提取或视觉模型，检查金额与表头能否对应。先用真实文档类型建立题集，再判断更复杂的视觉链路是否值得投入。

若问题需要跨实体关系或对大批资料进行主题总结，可以研究 GraphRAG，并与当前混合检索基线比较；它会引入关系抽取、图结构和额外维护成本。若岗位强调模型适配，再学习 LoRA 的数据与训练评测；若强调私有推理服务，再研究 vLLM、批处理、显存与吞吐。每条路线都应回到一个可测量的问题。

对于当前 AI 应用开发目标，先完成真实问答服务、小题集评测和四份交付材料，就可以开始项目演示与求职准备。目标岗位需要工具执行时，再选第 21—22 章的单 Agent 与 MCP，并用第 23 章验证业务结果。多 Agent 仅在明确任务分工、并行收益或独立上下文需求出现后比较。

实验二：从候选到指标

内置四道题中，第四道题同时需要培训制度和差旅指引。默认切分下的运行结果如下：

配置Hit@k平均 Recall@k第四题
k=11.0000.875找到两份所需资料中的一份，Recall=0.5
k=31.0001.000两份资料都进入候选

这是随附四题语料的离线检索实测结果，不能据此推出真实大模型回答质量。手算 (1+1+1+0.5)/4=0.875，再打开逐题输出核对。继续观察候选中混入的无关资料，就能把“召回更多”和“上下文更好”分成两个需要分别验证的问题。

实验中的 k 表示返回片段数，命中按不同文档计算。同一文档返回两个片段时，只计一次文档命中；缩小切分窗口以后，同一文档的多个片段也会竞争这 k 个候选位置。
